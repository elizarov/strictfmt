# Grammar Research

This document records grammar experiments that affect parser genericity and external-project coverage. Keep it current while exploring grammar changes, including failed attempts, so the final shape is justified by evidence rather than only by the passing fixture set.

## Genericity Rule

Grammar rules must compose through C++ nonterminals whenever the construct can appear in the corresponding C++ position. Do not add shallow productions that recognize one observed spelling plus one level of suffix, operator, argument, or member nesting. If a construct is an expression atom, it must enter the expression grammar as an atom and let the existing recursive expression grammar own calls, member access, operators, and statement termination.

Scanner tokens are acceptable only for lexical or line-aware classification that would otherwise expand the generated lexer or require runtime configuration. The parser still owns syntactic composition after the token is classified.

## Generated Parser Source Size

The generated C++ parser must remain one file no larger than 50,000,000 bytes while using the unmodified upstream tree-sitter runtime, parser ABI, and table readers. The accepted grammar at this checkpoint generates a 100,410,897-byte `parser.c` before source compaction, with 33,947 states, 14,471 large states, 813 symbols, 302 terminals, and 316 production IDs. All 52 tests pass at that baseline.

### Stock-Table Source Compaction

Status: accepted.

Shape: run the pinned unmodified tree-sitter CLI, then rewrite only redundant C spelling inside its monolithic parse-table declarations. Symbolic enum references become the same numeric enum values, `STATE(n)` and `ACTIONS(n)` become `n` after verifying that the pinned generated parser header defines both as identity macros, and leading table indentation is removed. The transformation does not split or re-encode a table, change a value or dimension, widen a type, modify a generated header, or require a runtime change. The regeneration tool rejects an output above the 50,000,000-byte limit.

Result: `parser.c` decreases from 100,410,897 to 37,297,300 bytes. Its 33,947 states, 14,471 large states, 813 symbols, 302 terminals, and 316 production IDs are unchanged. The source compiles against the vendored stock runtime and all 52 tests pass, including golden parse/idempotence tests and the CaseDash, GoogleTest, and userver corpus sweeps.

This is source compaction, not a private parse-table format. The runtime sees the same statically initialized arrays and the same `TSLanguage` structure that the stock generator emitted.

### Size-Reduction Alternatives

Status: measured and rejected or deferred.

The following experiments were performed against the same accepted grammar before choosing source compaction:

| Experiment | Generated bytes | Result |
| --- | ---: | --- |
| Force all generator states into the stock sparse-table representation | 83,229,621 | Insufficient reduction; rejected. |
| Inline five hidden one-state wrappers | 99,261,281 | Saved 26,307 bytes while adding four states; rejected. |
| Replace macro-argument items with one recursive token-tree rule | 97,787,084 | Saved about 1.5 MB but flattened useful CST structure; rejected. |
| Remove logical conditional-fragment binary paths | 98,413,370 | Follow-up required-edge checks broke the unsupported-output golden and a GoogleTest string parse; rejected. |
| Remove the macro-argument conditional-fragment binary path too | 96,860,753 | Broke the unsupported golden expression-fragment case; rejected. |
| Remove generated function-suffix fallback | 95,694,835 | Broke many supported external declarations; rejected. |
| Remove generated declaration-prefix fallback | 98,411,864 | Configured scanner categories could not recover the affected reductions before the generated identifier won; rejected. |
| Use ordinary `expression` for template arguments | 94,774,318 | Broke eight nested-template uses in userver; rejected. |
| Add upstream expression dynamic precedence to that template form | 94,781,128 | Preserved the same eight failures; rejected. |
| Use the exact upstream comma-list template shape | 94,179,168 | Still broke nested templates and removed supported conditional/macro template fragments; rejected. |
| Give template `<` lexical priority | 94,324,811 | Broke hundreds of ordinary template/relational contexts; rejected. |

The stock upstream C++ grammar regenerated with the same pinned CLI is 16,931,239 bytes with 8,499 states, 2,338 large states, and 535 symbols. Rule-state comparison shows that Strictfmt's extension ambiguity is multiplied most heavily through common expression roles: relative state-report increases include `binary_expression` +4,632, conditional expression +3,408, call expression +3,195, update expression +3,121, field expression +3,030, parameter-pack expansion +3,019, and subscript expression +3,009. Direct macro-list rules are much smaller; for example, `macro_argument_list` accounts for 287 reported states. Future grammar reduction should therefore target shared ambiguity at expression/context boundaries rather than shallow list-rule factoring.

Splitting `parser.c` is deferred as a last resort. It would not reduce the total generated source and is unnecessary while the semantics-preserving monolithic compaction remains below the enforced limit.

## 16-Bit Parser Reduction

The generated parser must fit the unmodified upstream tree-sitter ABI: parser state ids and parse-table action indexes must both be at most 65,535. Measure both after every grammar experiment; reducing only the state count is insufficient.

### Baseline

Status: measured.

The current generated parser has 74,113 states and a maximum parse-action index of 110,423. Its largest referenced shift state is 74,102. The baseline `scripts/test.sh` run passes all 50 tests. Reaching the upstream ABI therefore requires removing at least 8,578 states and 44,888 parse-action entries while preserving the current supported grammar and formatter behavior.

### Shared Common-Body Function Prefixes

Status: accepted.

Shape: replace the JavaScript helpers that textually expanded an ordinary function-definition prefix and a macro-function-definition prefix into each of the five `#if`/`#ifdef`/`#else`/`#elif`/`#elifdef` branch rules with two hidden grammar nonterminals. Hidden nodes promote the same children and fields, so the visible syntax tree and accepted branch shapes stay unchanged while the recursive declaration, declarator, macro-argument, and block-item graphs are generated once per prefix role.

Result: parser states decreased from 74,113 to 73,810, the maximum parse-action index decreased from 110,423 to 109,731, and generated `parser.c` decreased from 286,199,819 to 283,847,935 bytes. All 50 tests pass, including golden parse/idempotence checks and all external-project checks. This is a real reduction, but the action index remains 44,196 above the upstream limit, so broader sharing and conflict reduction are still required.

This is a historical checkpoint: the ordinary selected-prefix family was later removed after corpus auditing found no supported uses. The retained macro-function family still uses the hidden-prefix factoring introduced here.

### Shared Parameter-List Item Rules

Status: accepted with a marginal reduction.

Shape: extract hidden item nonterminals for normal parameter lists, `requires` parameter lists, conditional parameter branches, normal template-parameter lists, and conditional template-parameter branches. Each list retains its exact item set; in particular, only conditional declaration-parameter branches accept configured macro parameters, and only conditional template-parameter branches accept the leading-comma helper token. The first generation attempt exposed an ambiguity between the literal `...` parameter item and a unary left fold, so the final shape declares that narrow conflict explicitly.

Result: relative to the shared-function-prefix parser, states decreased from 73,810 to 73,807 and the maximum parse-action index decreased from 109,731 to 109,682. Generated `parser.c` increased slightly from 283,847,935 to 283,856,817 bytes, showing that source-level factoring is not a reliable proxy for table size. All 50 tests pass. The centralized item definitions are retained, but the tiny table reduction confirms that larger gains must come from collapsing the macro/declaration ambiguity network rather than factoring list choices alone.

### Unified Macro-Interleaved String Token

Status: accepted.

Shape: merge the two terminals for macro-leading and string-leading sequences of interleaved string literals and macro identifiers. Their regular languages have disjoint leading forms, they were always accepted together by `concatenated_string`, and the formatter does not distinguish their internal token kinds. The unified terminal keeps both regex alternatives and the higher existing lexical precedence, so token spans and formatted output stay unchanged.

Result: the terminal count decreased by one. Parser states stayed at 73,807, while large states decreased from 37,496 to 37,467, the maximum parse-action index decreased from 109,682 to 109,258, and generated `parser.c` decreased from 283,856,817 to 282,275,471 bytes. All 50 tests pass. Removing a broadly reachable symbol provides a materially better action-table and byte-size reduction than list-item factoring, but the action index is still 43,723 above the upstream limit.

### Grouped Macro-Argument Fallback Tokens

Status: rejected.

Shape: group seventeen macro-only token fallbacks into four terminals according to their existing lexical precedence. The grouped regex choices preserved the same token languages and priorities and removed thirteen named terminals from `_macro_argument_list_item`.

Result: terminal and symbol counts each decreased by thirteen, and generated `parser.c` decreased from 282,275,471 to 281,990,577 bytes. Parser states remained 73,807 and the maximum parse-action index remained 109,258, so the experiment made no progress toward either 16-bit limit while coarsening the internal token tree. It was reverted without running the full suite. Terminal columns affect generated bytes, but these macro-argument fallback symbols do not account for the oversized state/action graph.

### Merged Contextual `#if` And `#ifdef` Families

Status: rejected.

Shape: for every non-base conditional placement, merge `#if` with `#ifdef`/`#ifndef` into one contextual open rule and merge `#elif` with `#elifdef`/`#elifndef` into one contextual alternative rule. The generic top-level preprocessor rules and bespoke common-body rules stayed separate. This reduced each contextual family from five rules to three while retaining every directive spelling and branch body.

Result: contextual `ifdef`/`elifdef` symbols and their dedicated conflicts disappeared, reducing the symbol count by twenty-five. However, the shared header choices widened every remaining contextual state: parser states increased from 73,807 to 75,506, the maximum parse-action index increased from 109,258 to 111,170, and generated `parser.c` increased from 282,275,471 to 287,832,830 bytes. The experiment was reverted without running the full suite. Separate directive-header rules let the LR generator keep narrower lookahead sets and are substantially smaller than a shared header choice.

### Localized Per-CPU Parameter Annotations

Status: rejected.

Shape: remove `macro_annotated_declarator`, its field and abstract variants, and their global alternatives from `_declarator`, `_field_declarator`, and `_abstract_declarator`. Those wrappers are indirectly recursive through the pointer, reference, handle, member-pointer, and parenthesized declarator families. Replace them with a parameter-local post-type annotation slot; the existing declaration, field, function-definition, and type-descriptor slots already cover the other observed `__rseq_percpu` placements. A userver golden fixture was added for the previously untested return/local declaration, named pointer parameter, and cast shapes because `external/userver/.cpp-format-ignore` excludes the librseq source files that contain them.

Result: the terminal count decreased by one and the symbol count decreased by six, but the local parameter alternative widened a high-fanout grammar path. Parser states increased from 73,807 to 75,161, the maximum parse-action index increased from 109,258 to 110,424, and generated `parser.c` increased from 282,275,471 to 285,773,243 bytes. The grammar experiment was reverted without running the full suite; the focused golden coverage was retained because it exercises behavior supported by the restored grammar.

### Normalized Function-Suffix Declarators

Status: accepted.

Shape: remove `macro_suffixed_function_declarator` and `macro_suffixed_function_field_declarator` from the recursive declarator graph, including the redundant qualified-return-type alternative. Both bespoke rules duplicated suffix placements already accepted by `_function_declarator_seq`: function suffix macros may occur in `_function_attributes_start` immediately after the parameter list or in either `_function_attributes_end` slot around the trailing return type and postfix. The normal rules accept the same token sequences and preserve the visible children and fields without a second recursive copy of the parameter, attribute, ref-qualifier, exception, trailing-return, and postfix sequence. Ordinary uses are intentionally canonicalized from the bespoke node kind to `function_declarator`; field and qualified-return uses already aliased the bespoke node to `function_declarator`. The formatter had no model registration for the removed node, so this replaces its generic-tree handling with the normal function-declarator model.

Result: parser states decreased from 73,807 to 65,039, the largest referenced shift state decreased to 65,029, the maximum parse-action index decreased from 109,258 to 98,621, and generated `parser.c` decreased from 282,275,471 to 257,042,720 bytes. All 50 tests pass, including the GoogleTest and userver external-project sweeps and golden suffix-macro fixtures. The parser now fits the 16-bit state-id limit, but its parse-action index remains 33,086 above the upstream limit. Historical measurements show that action offsets, rather than state ids, remain the completion gate.

### Current Upstream Generator Control

Status: rejected as a solution.

Shape: generate the accepted normalized-suffix grammar with the official tree-sitter CLI 0.26.9 using ABI 14 instead of the pinned 0.24.7 CLI. This isolates generator state-merging changes from grammar changes while retaining the language ABI used by the project.

Result: CLI 0.26.9 reports a parse-table action count of 98,623 and refuses to write the parser because the count exceeds 65,535. This is the count form of the pinned generator's maximum valid action index 98,621: indexes start at zero and the generated table reserves its final boundary. The newer generator therefore provides no material table reduction and instead enforces the upstream limit earlier. The pinned generator remains necessary for measuring oversized experiments; completing the migration still requires grammar changes.

Follow-up after the grammar fits the upstream limits: stock CLI 0.26.9 at ABI 14 now emits the parser successfully. It preserves 39,395 states, 18,875 large states, 827 symbols, 308 terminals, 322 production IDs, and maximum action index 62,171, but produces a 138,191,474-byte `parser.c`. That is 133,089 bytes larger than pinned CLI 0.24.7's 138,058,385-byte output for the same narrowed-fallback grammar. Updating the upstream generator is therefore not a byte-size reduction either; the pinned output remains retained.

### Name-Only Tagged Type Arguments

Status: accepted.

Shape: keep tagged type references as ordinary argument-list items, but replace complete `struct_specifier`, `union_specifier`, `enum_specifier`, and `class_specifier` productions with name-only sequences aliased to those same visible node kinds. The documented and observed macro use is `offsetof(struct tag, member)`-style syntax. Accepting complete inline tagged definitions in the same ubiquitous call-argument position unnecessarily imported class bodies and their recursive field/declaration graph into call-expression states.

Result: parser states decreased from 65,039 to 64,561, the maximum parse-action index decreased from 98,621 to 98,190, and generated `parser.c` decreased from 257,042,720 to 255,085,113 bytes. All 50 tests pass, including external-project sweeps, the librseq-shaped tagged argument coverage, and the constructor/member-initializer suffix fixture added after the preceding checkpoint. The visible tagged-specifier node names and `name` field are preserved.

### Declaration-Only Prefix Macro Scope

Status: accepted.

Shape: remove `macro_prefixed_type_specifier` from `type_specifier` and delete its dedicated conflict. The recursive rule allowed a `DeclarationPrefixMacros` item to wrap any type-specifier occurrence, including casts and template/type-expression contexts, and could wrap another macro-prefixed type. The documented role is a declaration/definition prefix, which `_declaration_specifiers` already accepts through `_declaration_modifiers`; class heads and the narrow storage-class fallback have their own owned prefix slots.

Result: parser states decreased from 64,561 to 64,171, the maximum parse-action index decreased from 98,190 to 98,002, and generated `parser.c` decreased from 255,085,113 to 253,191,488 bytes. All 50 tests pass, including configured declaration-prefix macros throughout GoogleTest and userver. The accepted grammar now implements the macro category only in the declaration positions owned by `docs/macro.md`.

### Centralized Post-Type Annotation Boundary

Status: accepted after remeasurement at the reduced grammar checkpoint.

Shape: remove the three indirectly recursive `macro_annotated_*declarator` families and their reserved per-CPU terminal, then move the missing parameter role into the existing hidden `_declaration_specifiers` tail as `post_type_macro_annotation`. Remove redundant annotation repeats immediately after `_declaration_specifiers`, while retaining explicit slots for type paths that bypass it. This avoids the competing parameter alternative from the earlier failed experiment and gives observed annotations one shared type/declarator boundary.

Initial result: the direct shared-tail form reduced the symbol count by five and the terminal count by one. States decreased from 64,171 to 63,932 and generated `parser.c` decreased to 250,881,117 bytes, but the maximum parse-action index increased from 98,002 to 98,081. A follow-up removed the duplicate first-declarator annotation routes by splitting declaration and field lists into hidden first/subsequent items, retaining annotation support after commas and adding explicit slots only to type paths that bypass `_declaration_specifiers`. That form was worse on both gates: 64,482 states, action index 98,511, and a 252,657,778-byte parser. Both variants were isolated and reverted while the action index was the binding constraint.

Final result: after the 16-bit reductions, the direct shared-tail form improves every metric. Against the 40,907-state, 150,613,571-byte upstream-ABI checkpoint, states decrease by 1,512 to 39,395, large states by 321 to 18,875, maximum action index by 1,679 to 62,235, symbols by five to 827, terminals by one to 308, production IDs by six to 322, and generated `parser.c` by 6,422,588 bytes to 144,190,983. All 50 tests pass. An exact 5,048-file audit finds no clean-file regression: eight CST hashes change in the two userver-style golden files, one GoogleTest file, and five userver files. Recovery improves from 12 to 10 errors in GoogleTest's already-invalid `gmock-matchers.h` tree and from three to two in ignored RapidJSON `internal/stack.h`; all missing-node totals are unchanged. The retained form removes the recursive normal/field annotation declarators and their reserved terminal, adds post-type annotations once to `_declaration_specifiers`, removes the now-redundant immediate function/inline-method repeats, and keeps the shared declarator-list slots needed by qualified type paths that bypass `_declaration_specifiers`.

### Pruned Macro-Prefix Wrapper Targets

Status: rejected.

Shape: retain `macro_prefixed_function_definition`, `macro_prefixed_declaration`, and `macro_prefixed_field_declaration_item` only for targets whose normal heads bypass declaration modifiers: qualified-type and macro-function forms. Remove normal function/declaration/field, constructor/destructor, and operator-cast targets because their existing declaration or constructor specifier sequences already accept `function_prefix_macro`.

Result: parser states decreased by only fifteen, from 64,171 to 64,156, while the maximum parse-action index increased from 98,002 to 98,032. Generated `parser.c` decreased slightly to 252,884,545 bytes. The compact wrapper references are not a meaningful source of the remaining action fan-out, and narrowing their high-precedence disambiguation is not justified by a worse binding metric. The experiment was isolated and reverted without running the full suite.

### Scoped Branch-Owned Leading Separators

Status: accepted.

Shape: split the conditional comma-list helper according to the placement contract in `docs/preprocessor.md`. Argument, subscript, declaration-parameter, and `requires`-parameter lists retain normal items and conditional items whose selected payload may own a trailing comma. Only template-parameter lists use the additional whole-list alternative where a conditional follows an existing item without its comma and therefore owns the leading separator. Constructor field-initializers already use a separate constructor-specific leading-comma rule and are unchanged.

Result: four generated auxiliary symbols disappeared. Parser states decreased from 64,171 to 63,388, the maximum parse-action index decreased from 98,002 to 97,342, and generated `parser.c` decreased from 253,191,488 to 251,556,893 bytes. All 50 tests pass, including the `format_ifdef` actual-shape fixtures for each supported list position, template branch-owned leading commas, constructor initializer leading commas, and the external-project sweeps.

### Canonical Function-Suffix Ownership

Status: rejected.

Shape: remove suffix macros from the generic start-attribute slot, add an anchored suffix-before-ref/exception path, let the first end slot own ordinary and pre-trailing/postfix suffixes, and make the final end slot reachable only after an actual trailing return or postfix. This gives every observed suffix run one owner instead of allowing the same tokens through two or three nullable slots.

Result: despite the cleaner ownership, the anchored prefix choice widened the function-declarator graph: states increased from 63,388 to 64,037, the maximum parse-action index increased from 97,342 to 97,733, and generated `parser.c` increased to 252,692,559 bytes. A narrower follow-up restored the existing suffix start path, retained only a tail-anchored final slot, and algebraically removed overlaps inside the attribute-specifier/type-qualifier and attribute-specifier/attribute-declaration choices. That form produced 63,409 states, action index 97,339, and a 251,351,710-byte parser: only three action entries gained at the cost of twenty-one states and formally narrowing adjacent heterogeneous end groups without a trailing return or postfix. Neither tradeoff materially advances the completion gate, so both variants were isolated and reverted without running the full suite.

### Statement-Sequence Macro Argument Scope

Status: accepted with a marginal reduction.

Shape: remove `macro_statement_sequence_argument` from the ubiquitous `_macro_argument_list_item` choice while retaining it as a direct alternative of `macro_call_statement_argument`. Before statement-argument macros had their own scanner category and first-argument list, the generic macro argument list needed this structured statement fallback. The dedicated path now owns it: `docs/macro.md` specifies that only the first argument of a configured statement-argument macro has statement syntax, while subsequent arguments use ordinary macro-argument syntax. The narrow raw statement-sequence token remains available in generic macro arguments because it is a terminal fallback and does not import the recursive statement graph.

Result: parser states decreased from 63,388 to 63,384, the maximum parse-action index decreased from 97,342 to 97,340, and generated `parser.c` decreased from 251,556,893 to 251,360,846 bytes. All 50 tests pass, including structured statement-argument fixtures and both external-project sweeps. The tiny table change confirms that the dedicated scanner category had already isolated most of the statement graph, but removing the stale alternative makes the implemented role match its documented ownership. The raw fallback remained at this checkpoint; the later zero-owner macro/replacement audit removed it after no corpus source reduced through it.

### Statement-Argument Macro Expression Scope

Status: accepted.

Shape: remove `macro_statement_argument_call` from the global `_expression_not_binary` atom set and make configured statement-argument macro calls compose only through statement-owned paths. A hidden expression rule owns a direct call or a recursively left-associated stream-insertion chain; aliases preserve the normal visible `binary_expression` and `expression_statement` node kinds. The same hidden rule remains available as the first item of a nested statement-argument macro list, and both single-expression and statement-sequence macro items preserve their previous CST wrappers. Ordinary expressions no longer inherit the complete statement-argument macro call graph merely because the configured call can appear as a statement.

Corpus evidence supports the narrower role. Of 4,265 configured statement-argument macro calls in the golden fixtures, casedash, GoogleTest, and userver, 3,873 were direct semicolon-terminated statements, 319 were followed by `<<`, and 66 were nested in another configured statement-argument macro. No configured call occurred as a return value, assignment operand, initializer, condition, top-level expression, or other general expression; the only observed postfix composition was `<<`. The userver configuration now includes GoogleTest's `EXPECT_FATAL_FAILURE` and `EXPECT_NONFATAL_FAILURE` wrappers, and retained golden fixtures cover direct, streamed, nested-stream, and nested statement-sequence shapes.

Result: parser states decreased from 63,384 to 62,624, large states decreased from 32,899 to 32,444, the maximum parse-action index decreased from 97,340 to 96,141, and generated `parser.c` decreased from 251,360,846 to 246,265,838 bytes. All 50 tests pass, including golden parsing and idempotence plus the GoogleTest, userver, and casedash external-project sweeps.

### Canonical Type-Producing Macro Declarations

Status: accepted.

Shape: remove the complete `type_specifier_macro_declaration` and `type_specifier_macro_type_definition` wrappers, their declaration/type-definition alternatives, and the two conflicts that existed only to select the declaration wrapper. A configured `TypeSpecifierMacros` call already enters the ordinary grammar as `type_specifier`; normal declaration and inherited type-definition productions therefore own the declarator list, declaration modifiers, optional initializer, suffix conditional, and terminating semicolon. The wrappers duplicated complete outer productions around the same type atom and imported their declarator graphs into a second ambiguity path.

Result: parser states decreased from 62,624 to 61,543, large states decreased from 32,444 to 31,784, the maximum parse-action index decreased from 96,141 to 94,787, and generated `parser.c` decreased from 246,265,838 to 242,242,051 bytes. All 50 tests pass, including configured type-producing macro uses in GoogleTest, userver, and casedash. The visible type macro call and ordinary declaration/type-definition structure are preserved; only the redundant complete-wrapper node kinds disappear.

### Shared Constructor/Destructor Header

Status: accepted with a context-dependent reduction.

Shape: replace the JavaScript `constructorOrDestructorHeader` helper, which textually expanded the recursive declarator sequence into ordinary definitions, declarations, field definitions, and every conditional branch rule, with one hidden `_constructor_or_destructor_header` nonterminal. Replace five branch-specific declarator conflicts with one conflict against the shared hidden role. Hidden-child and field promotion preserve the same visible aliased `function_declarator` child and `declarator` field; generated `node-types.json` is byte-identical.

Result: against the canonical type-producing-macro checkpoint, parser states decreased from 61,543 to 61,395, large states decreased from 31,784 to 31,731, the maximum parse-action index decreased from 94,787 to 94,707, and generated `parser.c` decreased from 242,242,051 to 241,971,757 bytes. All 50 tests pass, including RapidJSON's template and non-template selected constructor headers and all external-project sweeps. An earlier isolated experiment before the type-producing-macro cleanup measured a much larger 892-state and 1,279-action reduction; after that cleanup removed overlapping recursive declarator ambiguity, the cumulative gain is only 148 states and 80 actions. Parser-table reductions are therefore measured in sequence rather than assumed to add.

### Raised-Precedence Macro Return Type Normalization

Status: rejected after external-project validation.

Shape: add `macro_return_type_specifier` to the ordinary `type_specifier` alternatives, remove the complete `macro_return_function_definition` wrapper and its template/friend aliases, and raise the type macro's precedence by one so normal function definitions can own the remaining declarator and body. This canonicalizes the RapidJSON-style return-type macro through the same declaration path as configured `TypeSpecifierMacros` calls.

Result: against the 61,543-state canonical type-producing-macro checkpoint, parser states decreased to 60,295, the maximum parse-action index decreased from 94,787 to 93,574, and generated `parser.c` decreased to 238,679,372 bytes. The raised precedence was not behavior-preserving: it captured configured `macro_function_definition_with_trailing_parameters` headers before their second parameter list, and the full suite failed four tests across six userver benchmark files. The experiment was reverted. A future normalization must resolve the two complete header roles structurally instead of deciding them by higher static precedence.

### Scanner-Only Macro-Call Fallback Removal

Status: rejected as an isolated reduction.

Shape: remove the generated `macro_call_expression_identifier_fallback` and `semicolonless_macro_call_identifier_fallback` terminals plus their two wrapper nonterminals, and use the configured `call_syntax_macro_identifier` directly in expression, item, block-line, and top-level-line macro-call roles. Project configs can classify the observed spellings, so this tests whether the duplicate generated/external lexical routes are themselves a major table contributor.

Result: against the 61,395-state shared-constructor checkpoint, states decreased by 25 to 61,370 and generated `parser.c` decreased by 2,535,754 bytes, but large states increased by 65 and the maximum parse-action index increased by 442 to 95,149. The isolated change was reverted without running the full suite. A broader fallback-removal upper bound is substantially smaller because terminal removals interact non-additively, but this macro-call subset must not be retained or credited independently unless a later combined checkpoint is validated as a whole.

### Single-Owner Conditional Initializer Lists

Status: accepted.

Shape: replace the choice between the inherited complete `initializer_list` and a second complete `preproc_fragment_initializer_list` with one visible `initializer_list` that owns the braces and optional trailing comma. Ordinary items use the normal comma-separated interior. A hidden `_initializer_list_with_preproc` interior preserves the previous required-preprocessor path exactly: any number of comma-terminated leading items, a first structured directive or conditional fragment, repeated directive/item combinations, and an optional final item. The two existing comma-expression conflicts move from the deleted visible wrapper to the hidden interior. Hidden-child promotion puts directive and item children directly under the one normal initializer-list node; both old visible list kinds already used the same formatter model and classes, so formatted output is unchanged.

Result: deleting conditional/local-directive initializer support entirely established an upper bound of 59,203 states and action index 91,657, reductions of 2,192 states and 3,050 actions. The language-preserving shared-outer form retains 860 of those state reductions and 1,030 action reductions: states decreased from 61,395 to 60,535, large states from 31,731 to 31,298, maximum action index from 94,707 to 93,677, and generated `parser.c` from 241,971,757 to 238,742,210 bytes. All 50 tests pass. A focused RapidJSON-style initializer containing `#define`, generated items, and `#undef` parses through the hidden required-preprocessor path; its output is byte-identical to the prior parser, reparses, and is idempotent. Only the redundant nested initializer-list wrapper disappears from the visible CST.

### Standard Block And Linkage Ownership

Status: accepted.

Shape: replace the inherited `_block_item` expansion with the constructs that can actually occur in a C++ compound statement: declarations and type definitions, statements, empty declarations, local preprocessor directives and supported conditional forms, local macro-call lines, namespace aliases, using/alias/function-type declarations, and static assertions. Direct nested function definitions, templates, namespace/module/concept definitions, linkage specifications, constructors/operators, and top-level decorator/generator roles are not valid compound-statement items; macro replacements retain their own complete declaration/definition item owner. Preserve the dedicated alias for qualified-type declarations so their visible declaration children stay flattened. The inherited `declaration_list` was also incorrectly backed by `_block_item`; make it repeat `_top_level_item` so `extern "C" { ... }` continues to own function definitions and guarded declarations without putting them back into ordinary blocks. Removing `_block_item` as a competing guarded-macro-body reduction narrows the corresponding conflict to `statement` and `preproc_macro_call_body`.

Result: against the single-owner initializer checkpoint, states decreased from 60,535 to 59,141, large states from 31,298 to 30,478, maximum action index from 93,677 to 92,159, and generated `parser.c` from 238,742,210 to 228,518,499 bytes. The isolated coarse cut found two ownership omissions: a qualified declaration alias affected one golden layout, and userver's `exception_hacks.cpp` needs function definitions in an `extern "C"` declaration list. Restoring those through their legal owners cost only five states and six actions relative to the coarse upper bound. All 50 tests pass, including every external-project sweep and golden idempotence check.

These results are deliberately not combined arithmetically: generated terminals change which LR states merge, so fallback-removal interactions are strongly non-additive.

### Role-Specific Scanner Projections For Suffixes And Qualified Prefixes

Status: rejected as a reduction.

Shape: replace the generated function-suffix and macro-qualified-identifier fallbacks with two private external tokens that still query the existing `BareIdentifierMacros` configuration. Alias the role tokens back to the visible `bare_macro_identifier` node, and prioritize a role projection when its parser state explicitly requests that token. This gives ambiguous suffix and qualified-prefix states a scanner symbol distinct from the ubiquitous general bare-macro role without adding a user-facing macro category.

Result: against the 59,141-state block/linkage checkpoint, generated `parser.c` decreased by 10,831,223 bytes, but states increased by 211 to 59,352, large states increased by 30, and maximum action index increased by 70 to 92,229. Symbol and token counts were unchanged because two generated terminals were replaced by two external terminals. The experiment was reverted without compiling or running tests. Role-specific lexical identity reduces generated lexer columns, but the extra external parse-table distinctions work against both 16-bit gates.

Follow-up at the 138,058,385-byte narrowed-fallback checkpoint: the two projections now reduce generated C by only 858,283 bytes, while increasing states by 77 to 39,472, large states by seven to 18,882, and maximum action index by nine to 62,180. More importantly, the full suite fails five methods across both golden and external-project coverage. A reduced `void f() GTEST_LOCK_EXCLUDED_(x);` shows the core problem: the scanner is asked for and returns the configured suffix projection, but the parser has already reduced the preceding function declarator and recovers the macro as a second declarator. Restoring the generated terminal's precedence on the projected grammar increases the table to 39,553 states, 18,904 large states, action index 62,556, and 137,406,271 bytes without fixing the parse. Both variants were reverted. A private external token cannot substitute for the generated lookahead in this reduction conflict even though it consults only the configured bare-macro category.

### Removed Guarded Macro-Call Conditional Family

Status: rejected at this checkpoint; superseded by the later accepted removal.

Shape: remove the bespoke `preproc_macro_call`, body, and alternative family plus its ten conflicts, and rely on the normal top-level, block, and field contextual conditional families to select semicolonless macro-call items. The removed visible nodes had no formatter-model registration, while the replacement `preproc_if*`, branch, and `macro_call_item` kinds are registered. Three actual-shape golden blocks were added for a GoogleTest namespace-scope guarded call with alternatives, a userver block-scope generator call, and a RapidJSON class-scope generator call.

Result: the isolated deletion initially looked promising: against the 63,388-state, 97,342-action checkpoint it produced 63,231 states, action index 97,028, and a 250,761,418-byte parser. Combined with the statement-sequence cleanup it produced 63,227 states and action index 97,026. The new fixtures exposed why the apparently redundant family existed. The broad atomic conditional declaration-modifier token captured call-shaped one-line branches and left a pending declaration indent before a closing brace. Narrowing that token and explicitly adding configured `function_prefix_macro` items to contextual branches preserved configured declaration-prefix calls, but increased the table to 63,247 states and action index 97,277. Configured call-syntax alternatives then reduced as ordinary expression statements with missing semicolons, so explicit high-precedence macro-call items were also added; that form produced 63,275 states and action index 97,305.

The final form still failed four tests. A block-scope `RET_NAME(kNull)` conditional was captured by the atomic `preproc_expression_item_fragment`, causing the enclosing function to recover as a declaration with a braced initializer and leaving a missing semicolon at the next function. The changed recovery also added an unexpected missing-brace diagnostic to the error fixture. A closing-brace printer reset would hide only the indentation symptom while retaining raw macro classification and the parse recovery. The experiment was therefore reverted at this checkpoint. The actual-shape fixtures were retained and now protect the normal contextual conditional owners that made the later removal safe.

Follow-up after restoring the family: the broad atomic declaration-modifier token can still legitimately win for a one-call guarded block. When that conditional is the final item before `}` or `};`, its pending declaration indent must not override the closing brace's own frame. `PrintRightBrace` now flushes preceding content and then clears that pending indent before positioning any non-compact closing brace. All 50 tests pass with the retained namespace, block, and class fixtures, including golden idempotence and both external-project sweeps.

Final disposition: subsequent block-item, semicolonless-call, and precedence changes moved every supported guarded-call shape onto the ordinary contextual families. A later 5,048-file audit found no raw use of the bespoke family, and its removal preserved every supported CST; see **Removed Unused Guarded-Macro And Leaf Paths** above.

### Compound Statements In Argument Lists

Status: rejected as a reduction.

Shape: measure two independent removals of `compound_statement`. The first removes it from ordinary `_argument_list_item`, where normal braced arguments remain covered by `initializer_list` and configured statement-argument macros retain their dedicated statement path. The second removes it only from `_macro_argument_list_item`; statement-argument macro lists again retain their dedicated compound-statement alternatives. A corpus scan found no direct block argument among 16,486 configured `CallSyntaxMacros` uses in the fixtures, casedash, GoogleTest, and userver.

Result: against the 63,227-state, 97,026-action checkpoint, removing the ordinary-list edge produced 63,219 states, action index 97,011, and a 250,479,765-byte parser. Removing the macro-list edge instead produced 63,226 states, action index 97,023, and a 250,549,585-byte parser. The full block graph is already reachable through other expression and macro paths, so neither apparently high-fanout edge materially reduces the table. Both experiments were isolated and reverted without running the full suite; their small gains do not justify narrowing undocumented block-argument compatibility.

### Flat Contextual Preprocessor Alternatives

Status: rejected as a generated-table no-op.

Shape: rewrite the shared `preprocIf` helper so each opener owns a repeated sequence of `#elif`/`#elifdef`/`#elifndef` sibling nodes followed by an optional final `#else`, instead of letting each `preproc_elif*` node recursively own the next alternative. The two grammars describe the same directive language and retain the same visible branch node kinds, fields, body rules, precedence, and source order; only the raw CST branch topology changes from a chain to siblings. This appeared promising because it removes sixty-eight direct branch-to-branch edges across seventeen contextual families.

Result: tree-sitter normalized both formulations to byte-for-byte identical generated `parser.c` and `node-types.json` files: 63,384 states, 32,899 large states, maximum action index 97,340, and a 251,360,846-byte parser. The experiment was isolated and reverted without running the full suite. As with common-body source factoring, the generated LR graph—not the apparent JavaScript grammar recursion—is authoritative; alternative-chain flattening cannot reduce this table.

### Byte-Size Continuation Baseline

Status: accepted.

After the parser fit the upstream 16-bit ABI, the next gate was a decimal 100 MB generated-file limit: `vendor/tree-sitter/tree-sitter-cpp/src/parser.c` must be at most 100,000,000 bytes. The continuation retained the recursive C++ owners and made the following independently validated cleanups before the final three reductions below:

- one recursive template-argument-list interior replaced parallel before/after-fragment list alternatives;
- conditional initializer items moved from an opaque whole-list fallback to the normal visible initializer list, with the formatter removing branch-owned terminal commas under the ordinary non-enum trailing-comma rule;
- preprocessor string fragments kept a quote-led lexical boundary, guarded-assignment matching used an exact `#if` boundary so it could not consume `#ifdef`, and bounded line-repeat approximations were replaced with unbounded regular repetitions where the token language permits them;
- duplicate conditional-expression and macro-argument owners were removed when a narrower statement/list owner already retained the same recursive payload, including stale call-string and generic auto/return argument routes;
- `post_type_init_declarator` was folded into its only declarator-list owner, generated initializer and alias-suffix fallbacks were narrowed to their exact supported ambiguity spellings, and prefix/post-type/suffix annotation terminals remained role-specific rather than sharing one spelling language.

The resulting passing baseline was 101,902,271 bytes with 34,246 states, 14,706 large states, 810 symbols, 301 terminals, and 320 production IDs. The full formatter suite passed at this checkpoint. A simplified preprocessor-string regex was 69 KB larger and was rejected; removing the quote-led boundary also let a conditional fragment steal ordinary source following the directive.

### Canonical Qualified Declaration And Field Owners

Status: accepted.

Shape: fold the specialized qualified-type alternatives directly into the normal `declaration` and `field_declaration` rules. Remove the visible `qualified_type_declaration` and `qualified_type_field_declaration` wrappers and all redundant top-level, block, macro-prefix, and field-list aliases that led back to the same owners. The qualified type and the ordinary recursive declarator lists remain unchanged; only duplicate complete outer productions disappear. The separate qualified-return function-definition owner remains because attempts to force that ambiguity through general declaration specifiers were not language-preserving.

Result: states decreased from 34,246 to 34,198, large states from 14,706 to 14,660, symbols from 810 to 808, and production IDs from 320 to 316. Generated `parser.c` decreased by 267,411 bytes, from 101,902,271 to 101,634,860. Golden idempotence and all three external-project sweeps pass.

Rejected broader variants establish the boundary. Deleting the complete qualified-type declaration/function/field family produced a 100,484,129-byte parser but caused widespread ordinary qualified-type failures. Adding `_qualified_declaration_type` to `_declaration_specifiers` and deleting the parallel family produced 101,570,973 bytes, but three GoogleTest and eight userver files still failed; dynamic precedence did not repair them. The accepted change therefore canonicalizes only the two complete wrappers whose normal owners can preserve their exact recursive language.

### Conditional Initializer Choke-Point Scope

Status: accepted.

Shape: retain `_initializer_list_with_preproc` as the required-preprocessor choke point, but let its `preprocItem` contain only the contextual conditional initializer-list family. Remove direct `preproc_def`, `preproc_function_def`, and `preproc_call` alternatives. The closed placement contract supports recursively parsed conditional initializer items; local macro definitions and calls between initializer elements occur only in ignored third-party RapidJSON sources and are not a supported placement.

Result: states decreased from 34,198 to 33,724 and large states from 14,660 to 14,438. Generated `parser.c` decreased by 1,355,767 bytes, from 101,634,860 to 100,279,093, with symbol, terminal, and production counts unchanged. The `format_ifdef` parsing, formatting, and output-idempotence checks pass, as do the complete casedash, GoogleTest, and userver sweeps.

### Unified Generated Macro-Call Fallback

Status: accepted; completes the 100 MB gate.

Shape: merge the exact expression-only `GMOCK_KIND_OF_` terminal into `semicolonless_macro_call_identifier_fallback`, which already has the same lexical precedence and starts the same recursive `macro_argument_list`. Remove `macro_call_expression_identifier_fallback` and the one-alternative `macro_call_identifier_fallback` wrapper, and route both `macro_call_item` and `macro_call_expression` directly through the retained terminal. The expression role still owns macro-argument token language such as primitive type phrases; the consolidation changes only lexical identity and does not move anything to the scanner.

Result: states decreased by one to 33,723, symbols from 808 to 806, and terminals from 301 to 300; large states and production IDs remain 14,438 and 316. Generated `parser.c` decreased by 991,501 bytes, from 100,279,093 to 99,287,592. Removing a temporary, unnecessary dynamic-precedence wrapper from the conditional initializer interior reduced another four source bytes without changing any table metric. The final generated parser is **99,287,588 bytes**, 712,412 bytes below the decimal 100 MB limit. Its maximum action index is 52,851 and its largest referenced shift state is 33,714, both within the unmodified upstream 16-bit ABI. `scripts/test.sh` passes all 50 tests, including all golden parse/format/idempotence checks and every external-project sweep.

### Final Byte-Size Rejected Experiments

Status: rejected; recorded to prevent repeating non-composable reductions.

- Removing the generated macro-initializer fallback lost supported userver `ATOMIC_FLAG_INIT`; the retained exact two-spelling terminal is necessary because the generated identifier can win before scanner classification.
- Sharing one generated annotation terminal across declaration-prefix, post-type, and function-suffix roles made every spelling legal in all three positions. Despite reducing terminal columns, that violates the role-specific macro contract and was rejected. Exact role-specific terminals remain.
- Removing the two function-pointer alias rules produced 101,204,007 bytes but lost Windows, qualified-return, template-return, and member-pointer aliases. Combining pointer and non-pointer aliases inside `function_type_alias_declaration` produced 101,663,244 bytes, but ordinary GoogleTest function-type aliases selected the pointer branch and supported pointer aliases changed formatter structure. Both forms were reverted.
- Replacing the exact Windows primitive-return alias token with a structural primitive alternative produced 101,677,969 bytes when the calling convention was optional and 101,744,868 bytes when it was required. The first stole ordinary `void(args...)` function-type aliases; the second made the parser insert missing `__cdecl` tokens across all three external projects. The exact whole-alias fallback remains the narrowest language-preserving solution.
- Replacing `preproc_selected_else_if_body_item` with the complete recursive `_block_item` graph grew the parser to 103,091,885 bytes by importing every block ambiguity into the selected-prefix states. The narrower recursive statement/declaration subset remains.
- Removing only declared conflicts reported as unnecessary did not materially reduce the generated graph. Removing the structural delete-array path and broad qualified-type or alias families removed supported syntax. These changes were reverted rather than trading generic language for a small byte count.

## Experiments

### Shallow Preprocessor Expression Statement

Status: accepted after scanner cleanup.

Shape: parse a conditional preprocessor expression fragment, then manually accept a sequence of member/call/subscript suffixes and one optional operator before `;`.

Result: it handled selected fixtures such as a conditional `GTEST_SKIP()`/`FAIL()` followed by `<<`, but violated the genericity rule. The grammar had to know a bounded set of suffixes and operators, so one more nesting level required more special cases.

### Inline Normal Expression Statement Wrapper

Status: accepted.

Shape: add a high-precedence inline wrapper around normal `expression_statement`, with the conditional fragment as an expression atom.

Result: conceptually generic, but it introduced cascading tree-sitter conflicts between top-level expression statements, plain expressions, and type specifiers. Adding conflicts kept exposing broader ambiguities instead of converging on a stable grammar.

### Generated Complete-Fragment Regex

Status: rejected.

Shape: keep the parser generic, but use a larger generated token regex for conditional chunks whose branch lines appeared to end as complete expression atoms.

Result: tree-sitter generation succeeded, but the generated lexer exploded past the 16-bit parser state assumptions. The C compiler emitted many state/action conversion warnings with states around 99k, so this path is not viable.

### Scanner-Backed Expression Fragment With Continuation Peek

Status: rejected.

Shape: classify complete conditional expression fragments in the custom scanner and also consume following whitespace to verify that the next visible token was an expression continuation.

Result: focused formatting still worked, but consuming past `#endif` changed token spans and collapsed some unsupported-placement warning locations to `1:1`. External scanners must not consume a post-token lookahead only for classification.

### Scanner-Backed Expression Atom

Status: rejected and removed.

Shape: classify a conditional preprocessor block as `preproc_statement_expression_fragment` only when visible branch bodies look like complete expression-like atoms. The scanner declines control/declaration starters, attributes, configured bare/call-syntax macro identifiers, and operator-tail fragments. The parser accepts the token as an expression atom; normal recursive C++ expression grammar owns all surrounding calls, member access, operators, and statement termination.

Result: focused golden tests passed with this shape, but it made the scanner inspect conditional branch syntax and configured macro roles beyond simple token classification. That violates the scanner architecture rule. The external token and scanner helpers were removed; future support for these cases must be modeled in grammar/model space or remain an unsupported-placement warning.

### Scanner Conditional Header And Define Tokens

Status: rejected and removed.

Shape: classify selected macro-function headers and conditional blocks containing `#define` as multi-line scanner tokens. Both tokens started with the same `#if`/`#ifdef`/`#ifndef` prefix as normal conditional compilation, then scanned ahead to decide whether the guarded region had the special shape.

Result: the tokens were unsafe because an external scanner cannot consume an ordinary conditional prefix and then decline without blocking the generated grammar fallback. A tiny userver third-party repro failed:

```cpp
#ifdef X
ATOMIC_FLAG_INIT
#endif
```

`#ifdef X\n#define A 1\n#endif` still parses through the regular recursive preprocessor grammar after removing the scanner token. The scanner-token selected macro-function-header path was also a failed support experiment: it made GoogleTest's `TEST(...) { ... }` shared-body shape parse no better and was removed. Later structured grammar support for selected macro-function starts is documented separately below and in [preprocessor.md](preprocessor.md).

### Preprocessor Directive Argument Separators

Status: accepted.

Shape: make C++ preprocessor directive tokens that take a following argument consume the separating whitespace in the same way as `#if` already did. This covers `#ifdef`, `#ifndef`, `#elif`, `#elifdef`, `#elifndef`, and `#define`.

Result: simple `#ifdef` branches and ordinary conditional `#define` blocks parse through the normal recursive preprocessor grammar instead of recovering after the directive token. This is a lexical separator fix; it does not add any new supported conditional placement.

### GNU Named Variadic Macro Parameters

Status: accepted.

Shape: extend inherited C `preproc_params` with a structured `preproc_variadic_parameter` item for GNU named variadic macro parameters spelled `name...`.

Result: librseq macro definitions such as `#define rseq_mempool_free(_ptr, _stride...)` parse as normal preprocessor function definitions. This is a real preprocessor parameter-list shape and does not require scanner support.

Earlier attempt: adding a branch-local `preproc_bare_macro_item` as `bare_macro_identifier` followed by the existing `_line_break_whitespace` token generated and built, but the same tiny repro still failed at `#ifdef`, so explicit use of the hidden newline token did not put the parser in a state that asks the scanner for a bare macro identifier.

### Declaration-Suffix Conditional Modifiers

Status: accepted.

Shape: `declaration_suffix_preproc_ifdef` parses an `#ifdef`/`#ifndef` block after a complete declaration declarator list and before the terminating semicolon. Branch bodies may contain standalone identifiers, configured function-suffix macros, or attributes.

Result: userver's libc workaround prototypes use this for optional `__THROW` suffixes. The grammar already parsed the shape; marking the node as a supported preprocessor placement makes validation match the documented support list.

### C++ Function Type Declarator Suffixes

Status: rejected.

Shape: override `function_type_declarator` in the C++ grammar to use the same `_function_declarator_seq` as `function_declarator`, `function_field_declarator`, and `abstract_function_declarator`.

Result: the change is conceptually generic and makes C++ typedef function types such as `typedef R fwd_t(Args...) noexcept(noex);` parse through the normal type-declarator path. However, it expands the generated parser table past the runtime's 16-bit action ids; the C compiler emits thousands of `ACTIONS(...)` truncation warnings. This route is rejected unless the larger parser table issue is solved.

### Typedef Function Type Declarator Suffixes

Status: accepted.

Shape: override `_type_definition_declarators` so typedef declarators may be either the existing C `_type_declarator` or a `function_type_definition_declarator` whose declarator core is `_type_declarator` and whose suffix is the C++ `_function_declarator_seq`.

Result: the userver `function_ref.h` declaration `typedef R fwd_t(storage, _param_t<Args>...) noexcept(noex);` parses without putting the richer function suffix sequence into every type-descriptor context. Tree-sitter generation and C compilation stay below the action-id overflow threshold.

### Type-Qualifier Macro Category

Status: rejected.

Shape: add a `TypeQualifierMacros` use-side macro category and a scanner token that classifies configured identifiers separately from `BareIdentifierMacros`. Tried several parser entry points for qualifier-like macro fragments that appear in type positions, including a global `macro_suffixed_type_descriptor`, local `macro_qualified_type_descriptor` variants in cast/template contexts, an abstract-declarator qualifier fragment, and a `macro_qualified_type_specifier` atom.

Result: each grammar shape either introduced unresolved conflicts or expanded the generated parser table past the runtime's 16-bit action-id assumptions. The C compiler emitted `ACTIONS(...)` truncation warnings, ranging from roughly 499 warnings for the narrowest local descriptor variants to over 5600 warnings for the type-specifier atom variant. The separate scanner category was removed: the scanner should classify configured bare identifiers as `bare_macro_identifier`, and the grammar must decide where that token is accepted.

Retried the smallest direct hook by adding `bare_macro_identifier` to `type_qualifier`. Generation did not converge: the configured bare identifier role cascaded through conflicts with `top_level_item_macro`, `function_prefix_macro`, `calling_convention_macro`, and `macro_qualified_identifier`, including nested `(` and `template` contexts. The experiment was reverted before generating parser outputs.

### Bare Macros In Type Descriptors

Status: rejected.

Shape: keep the scanner category as `bare_macro_identifier`, but mirror C's `type_descriptor` shape with `repeat(choice(type_qualifier, bare_macro_identifier))` before and after the type specifier. This would parse C annotation casts such as `(void __rseq_percpu *)ptr` and cv/ref-like template arguments such as `std::decay_t<T> CVREF` through the normal type-descriptor nonterminal.

Result: tree-sitter generation converged only after adding several bare-identifier role conflicts involving `type_descriptor`, `function_prefix_macro`, `calling_convention_macro`, `top_level_item_macro`, and `macro_qualified_identifier`. The generated parser then crossed the runtime action-id limit; the C compiler emitted 144 `ACTIONS(...)` truncation warnings starting at `ACTIONS(65536)`. Rejected until the parser table representation is widened or a smaller generic grammar shape is found.

### Macro-Suffixed Type Descriptor Narrowing

Status: rejected.

Shape: add a narrower `macro_suffixed_type_descriptor` alternative that accepts a normal `type_specifier`, normal type qualifiers, one or more configured bare macro identifiers, and an optional abstract declarator. This targeted only suffix-like annotations instead of mirroring the full C type-descriptor shape.

Result: the smaller shape still crossed the runtime action-id limit after generation; the C compiler emitted hundreds of `ACTIONS(...)` truncation warnings starting at `ACTIONS(65536)`. Removed for now, so macro suffixes in type descriptors remain unresolved.

### Reserved Type-Qualifier Macro Fallback

Status: rejected.

Shape: add a generated `reserved_type_qualifier_macro` token to `type_qualifier`, limited to reserved double-underscore lower-case identifiers such as `__rseq_percpu`. This lets ordinary declaration-specifier and type-descriptor rules handle declaration, parameter, and cast positions through their existing recursive type-qualifier slots.

Result: generation finished, but the generated parser crossed the runtime's 16-bit state/action limits. The C compiler emitted tens of thousands of conversion warnings for states above 65535, including the `ts_small_parse_table_map` and `SHIFT(...)` tables. The experiment was removed. Future support for this shape needs either a still narrower local grammar hook or a widened parser table representation.

### Reserved Annotated Type Specifier

Status: rejected.

Shape: add a narrower `reserved_annotated_type_specifier` that accepts a normal `type_specifier` followed by one or more reserved double-underscore lower-case annotation macros. Use it only where the grammar already expects a declaration specifier's type or a cast/trailing-return `type_descriptor` type.

Result: generation completed, but the generated parser still crossed the runtime's 16-bit state/action limits. The C compiler emitted conversion warnings for states above 65535, including the small parse table and `SHIFT(...)` tables. This was smaller in concept than a qualifier-wide hook, but still too broad because it inserted another recursive `type_specifier` alternative into both declaration specifiers and type descriptors.

### Bare Macro Declaration Modifier Overmatch

Status: accepted.

Shape: split declaration-prefix macro identifiers into `DeclarationPrefixMacros`/`declaration_prefix_macro_identifier`, then use that token both in `_declaration_modifiers` and in the explicit recursive wrappers for macro-prefixed declarations, definitions, field declarations, and macro calls.

Result: bare namespace sentinels such as `USERVER_NAMESPACE_BEGIN` and `USERVER_NAMESPACE_END` no longer get absorbed as declaration prefixes for the following `template` or class declaration. Real prefix macros still compose through the dedicated `macro_prefixed_*` rules, so the grammar no longer relies on treating every configured bare identifier as a declaration specifier.

### Statement-Argument Member Calls

Status: accepted.

Shape: lower and narrow the fallback `macro_function_type_argument` token so normal C++ expressions win inside statement-argument and call-syntax macro argument lists. The fallback is limited to primitive function-type spellings, avoiding ordinary function or constructor calls that the expression grammar can parse structurally.

Result: configured throw/no-throw macros can still parse declaration-like first arguments such as `[[maybe_unused]] auto value = f()`, while ordinary member-call expressions whose receiver is itself a call, such as `std::move(fd).Close()` or `GetClient().ReadMany(request)`, compose through the normal expression grammar instead of being split after the receiver call. Call-syntax macro arguments that contain type fragments still parse structurally: the type-fragment argument remains a macro type fragment, and assignment arguments are handled by the normal expression grammar.

### Field-List Conditional Branch Items

Status: accepted.

Shape: include the field-list-specific preprocessor forms directly in `_field_declaration_list_item` and give that field-list form higher precedence than the generic `preproc_if`, so a conditional branch inside a class body parses through the same member-item grammar as the surrounding class body.

Result: class-scope conditionals can select constructor/destructor definitions with initializer lists, such as a move constructor guarded by `#if RAPIDJSON_HAS_CXX11_RVALUE_REFS`, without falling back to the generic block-item `preproc_if` shape.

### Constructor Header Suffix Fallback

Status: accepted.

Shape: allow constructor/destructor headers to consume configured function suffix macros immediately after the parsed function declarator, in addition to the normal suffix position already owned by `function_declarator`.

Result: conditional class-member branches no longer recover after a constructor declarator when the constructor has both a configured suffix macro and a member-initializer list, for example `C(C&& rhs) RAPIDJSON_NOEXCEPT : value(rhs.value) {}`.

Follow-up: suffix-only macros must stay in `BareIdentifierMacros`, not `DeclarationPrefixMacros` or `CallSyntaxMacros`, so the scanner can return the configured bare token when the grammar is in suffix position. Raising the precedence of the existing function-attribute slots, raising `function_declarator` dynamic precedence, and adding a direct suffix-macro repeat immediately after every parameter list all made tree-sitter generation hang after conflict analysis, so those shapes were rejected. The accepted shape keeps the existing suffix positions and raises only the local `function_suffix_macro` precedence so configured bare suffixes can win without adding a new grammar path.

### Call-Syntax Macro Statement Prefixes

Status: rejected.

Shape: allow `call_syntax_macro_identifier macro_argument_list statement` as a non-case statement. The body composes through the normal recursive `statement` nonterminal, so nested statements and blocks are handled by the same grammar as ordinary C++ statements.

Result: this was too broad. It made any configured call-syntax macro call in statement position a potential prefix for the following statement, so a sequence like `GMOCK_INTERNAL_PARSE_FLAG(verbose)` followed by `if (...)` could recover as a prefix macro body instead of two sibling statements. The shape was removed and no dedicated replacement category is kept without a current non-ignored source requirement.

Tried adding `optional(else_clause)` to this rule so if-like statement-prefix macros could own a following `else` through the same recursive shape as `if_statement`. Generation succeeded, but the parser crossed the runtime action-id limit; the C compiler emitted 445 `ACTIONS(...)` truncation warnings starting at `ACTIONS(65537)`. A narrower separate rule with a required `else_clause` hit the same limit and warning count. Removed for now. Do not reintroduce this broad statement/else composition without either shrinking the surrounding statement conflicts or widening the table representation.

### Configured Macro Calls In Enum Lists

Status: accepted.

Shape: extend the normal C++ `enumerator_list` so a configured `macro_call_item` can stand anywhere an enum-list item can stand, with or without a trailing comma, while preserving existing conditional/preprocessor entries.

Result: X-macro expansions such as `HTTP_ERRNO_MAP(HTTP_ERRNO_GEN)` parse inside `enum` bodies after the non-structural map/generator definitions are configured as raw. This is a use-side macro role in an enum-list position, not a special spelling for http-parser.

### Conditional Operator In Preprocessor Expressions

Status: accepted.

Shape: add `preproc_conditional_expression` to the inherited C preprocessor expression grammar, using normal conditional-operator precedence and recursive preprocessor-expression operands.

Result: `#elif defined(__BYTE_ORDER) ? (__BYTE_ORDER == __BIG_ENDIAN) : defined(__BIG_ENDIAN)` parses as a normal preprocessor condition inside field-list conditionals. This fixes userver's vendored librseq ABI header without a scanner token.

### Comma-Prefixed Conditional Parameters

Status: rejected.

Shape: support parameter-list conditionals where the conditional branch owns the comma before a selected parameter, for example `void f(int a #if X , int b #endif)`. The first attempt used a shared comma-list helper that accepted normal conditional list items and leading-comma conditional list items through the same recursive list shape, then applied it to function parameter lists, `requires` parameter lists, and template parameter lists.

Result: the shape was recursively generic, but too large for the current tree-sitter runtime table representation. The generated parser crossed the 16-bit action-id limit; the C compiler emitted 498 `ACTIONS(...)` truncation warnings starting at `ACTIONS(65537)`. A narrower version limited to function parameter lists still emitted 580 warnings. Splitting comma-prefixed parameters into a separate preprocessor-list rule made the table larger, with 1604 warnings starting at `ACTIONS(65536)`. All three shapes were removed. Do not reintroduce comma-prefixed conditional parameter support unless the parser table representation is widened or a smaller generic composition is found.

Follow-up: parameter-list and template-parameter-list conditionals now accept only complete branch items with an optional trailing comma. Removing the leading-comma alternative also fixes normal trailing-comma branches such as `std::string_view label,`, which had been misread as a branch-owned leading comma for another missing parameter.

### GNU Asm Template Macro Fragments

Status: removed after corpus audit.

Shape: extend the C++ `gnu_asm_expression` override so the assembly template can be either a normal string literal or a sequence of string literals, configured macro calls, and configured bare macro identifiers. ### Local Directives In Initializer Lists

### Post-Type Macro Annotations

Status: accepted narrowly.

Follow-up: generated fallbacks must stay narrow. A broader double-underscore lowercase fallback also matched Linux typedef spellings such as `__u32` and broke ordinary fields like `__u32 version;`. Do not replace this with broad all-caps matching or scanner spelling heuristics.

### Parameter-List Branch Leading Commas

Status: historical broad form rejected; superseded by scoped support.

Shape: allow preprocessor branch content in declaration parameter lists and template parameter lists to own an optional leading comma as well as a trailing comma. This targets generic list items that are present only in some configurations, for example `T& value` followed by `#if ... , std::enable_if_t<...>* = nullptr #endif`, and `template <class T #ifdef X , class = ... #endif>`.

Result: giving both list roles the same optional leading comma remained ambiguous, and declaration-parameter branches still do not own a leading separator. The later **Scoped Branch-Owned Leading Separators** change split the roles: declaration parameters support complete conditional items with optional trailing commas, while template parameters additionally support the tested branch-owned leading comma. The `format_ifdef` fixtures and [preprocessor.md](preprocessor.md) define the current contract.

### Raw Macro Definition Followed By Semicolonless Macro Calls

Status: accepted narrowly.

Shape: investigated semicolonless macro-generator runs after raw macro definitions, starting with `RET_NAME(...)` in `external/userver/universal/src/formats/yaml/exception.cpp`. The macro definition is raw because its replacement contains preprocessor stringification (`#type`). When the use-side spelling was configured as `CallSyntaxMacros`, the first use immediately after `#define` parsed as an ordinary call expression with a missing semicolon, while following identical uses parsed as `MacroCallItem`. Adding a blank or comment line after the `#define` also made the first use parse, which exposed a parser-state ambiguity rather than a scanner classification issue.

Result: the accepted fix removes the affected semicolonless generator spellings from userver `CallSyntaxMacros` and keeps their non-structural definitions in `RawMacroDefinitions` where needed. Corpus reduction later narrowed the exact generated terminal to the supported spellings that still lose to generated identifier recovery: `RET_NAME`, `UTILS_STRONG_TYPEDEF_REL_OP`, `RSEQ_INJECT_C`, `GMOCK_INTERNAL_PARSE_FLAG`, `GMOCK_KIND_OF_`, `THOUSAND_TESTS_`, `GTEST_IMPL_CMP_HELPER_`, and the exact GoogleTest diagnostic push/pop families present in the terminal. Semicolon-terminated block uses parse through a separate statement item that does not consume the line-break token; truly semicolonless uses parse through the line item. The same terminal can start a recursive `macro_call_expression`, so `GMOCK_KIND_OF_(unsigned long long)` retains macro-argument type syntax without a second expression-only terminal. This is a grammar-side lexical-ambiguity escape hatch, not a new scanner category and not a recommendation to configure plain function-like macro calls as `CallSyntaxMacros`.

Rejected attempts:

- A generated fallback for all macro-shaped call identifiers fixed `RET_NAME`, but regressed hundreds of userver files by stealing ordinary all-caps identifiers such as namespace macros before the grammar knew whether a macro argument list followed.
- A wrapper for `preproc_def` followed by `macro_call_item`, even with the explicit initializer-list conflict requested by tree-sitter, did not make the first use parse as a call-syntax macro.
- Raising raw macro-definition precedence and splitting raw-vs-structured macro definition names did not change the failure.
- Moving `macro_call_item` earlier in block and statement alternatives, removing the explicit `macro_call_item`/`expression_statement` conflict, and exposing `macro_call_item` through `bare_macro_statement` did not change the first-use state.

Scanner traces during the investigation showed that the first `RET_NAME` use was offered to the scanner only as `bare_macro_identifier`, while the later uses were offered as `call_syntax_macro_identifier` and parsed correctly. The accepted fallback therefore stays exact and local to spellings proven to need it; do not broaden this into all-caps matching or make the scanner return categories that were not configured.

### Recursive Expressions In Macro Arguments

Status: accepted.

Shape: remove `macro_string_concatenation_argument` and its component helper from `_macro_argument_list_item`. That high-precedence macro-only alternative recognized two or more adjacent string components, but the ordinary recursive `expression` alternative in the same list already owns concatenated strings and every expression that can contain them. ### Same-Line Runtime Macro Classification

Status: accepted.

Shape: reuse the existing hidden `_line_break_whitespace` external token as a narrow horizontal-only boundary when a configured statement-argument call follows in a non-preprocessor statement-argument state. Without that token boundary, the generated lexer could skip spaces and accept an ordinary identifier before the runtime scanner classified a configured macro. Letting the scanner fall through after consuming those spaces was also invalid because the spaces became part of the external identifier's source range. The scanner excludes preprocessor definition-name and replacement states and leaves every other horizontal gap to the generated lexer. The boundary advances tree-sitter to the identifier before classification, so the call composes through the existing recursive `statement` role whether it begins on the same line as an `if` condition, after a brace, or at the start of a line.

Result: `googletest/test/gtest_unittest.cc` no longer fails on the unbraced `EXPECT_THROW(ThrowNothing(), bool)` body. ### Configured Macros At Indented Preprocessor Branch Starts

Status: accepted.

Shape: extend the existing horizontal-only `_line_break_whitespace` boundary from configured statement-argument macros to every configured macro-identifier category accepted by the current parser state, but only when the horizontal whitespace is leading line indentation. The boundary remains conditional on an actual configuration match, continues to exclude raw preprocessor definition-name and replacement states, and still requires a following argument list for statement-argument macros. At non-leading horizontal gaps, statement-argument and type-specifier macros can use the boundary; type-producing calls need it after declaration keywords and modifiers such as `typedef` and `const`. Broadening non-leading gaps to every category regressed adjacent configured declaration macros such as `GTEST_API_ GTEST_DECLARE_STATIC_MUTEX_(...)`, so call-syntax, declaration-prefix, and bare categories retain leading-indentation-only handling. This is lexical ownership only: after the boundary advances the parser to the identifier, the grammar's existing role owns the complete construct.

The extension is needed when a configured macro is the first indented item after `#if` or `#ifdef`. The preceding `_preproc_directive_end` token consumes the directive newline but not the branch body's indentation. Without a horizontal boundary, the generated lexer can consume that indentation and classify the following spelling as an ordinary identifier before the runtime scanner gets another opportunity. Later branch items do not expose the bug because their preceding newline is consumed by `_line_break_whitespace` together with indentation.

Result: the first `MOCK_METHOD(int, CTNullary, (), (Calltype(STDMETHODCALLTYPE)))` in the Windows branch of `gmock-function-mocker_test.cc` retains its configured call-syntax role and reduces through `macro_method_declaration`. Type-producing calls such as `typedef GTEST_REMOVE_REFERENCE_AND_CONST_(T) RawT` and `using Address = const GTEST_REMOVE_REFERENCE_AND_CONST_(Type) *` also retain their configured role; `gmock-matchers.h` is removed from the exclusion list. This scanner-only change leaves the generated parser metrics unchanged.

### Preprocessing-Token Macro Arguments

Status: accepted with a configured category.

Shape: add `PreprocessorArgumentMacros` for function-like invocations whose arguments are preprocessing-token sequences instead of C++ expressions, types, declarations, or statements. A configured external identifier introduces a dedicated expression atom. Its outer argument list keeps top-level commas structured, while each argument recursively balances parentheses and accepts arbitrary non-delimiter preprocessing-token chunks plus normal string, character, raw-string, comment, and slash tokens. Only parentheses protect commas, matching function-like macro argument collection; brackets, braces, and angle brackets remain ordinary tokens. The format model preserves each complete argument as one atom, so token spelling and internal whitespace are not reinterpreted as C++ layout, while the surrounding call and argument-list breaks remain formatter-owned.

The grammar also removes the static precedence from the shallow semicolonless call-replacement item and retains its ambiguity with ordinary call expressions. This lets the complete recursive expression survive past the closing call parenthesis when an operator follows. Consequently, a structured replacement such as `JOINER_CAT(_Data, _N) = _Elem` parses as an assignment expression, while adjacent semicolonless generator calls still use the call-replacement sequence. Raising the general expression item's precedence did not help because the call-only reduction had already committed before the suffix; lowering only the call-item precedence had the same result. Keeping both interpretations at the actual call-expression conflict is the narrow generic fix.

Result: `EXPECT_EXPANSION` accepts deliberate token payloads such as `GMOCK_PP_CAT(+, =)`, `GMOCK_PP_HAS_COMMA(, )`, and `GMOCK_PP_IS_BEGIN_PARENS(sss() sss)` without broadening ordinary macro argument lists. `googlemock/test/gmock-pp-string_test.cc` is removed from the exclusion list. Relative to the preceding baseline, states increase from 33,697 to 33,947, large states from 14,431 to 14,471, symbols from 803 to 813, terminals from 300 to 302, maximum action index from 52,779 to 53,182, and largest referenced shift state from 33,688 to 33,938. Production IDs remain at 316. Stock generated `parser.c` increases from 99,212,287 to 100,410,897 bytes, and source compaction increases it from 36,988,236 to 37,297,300 bytes. All 52 tests pass, including focused configured/unconfigured token-argument coverage and the expanded GoogleTest sweep.

## Current External Unsupported Conditional Placements

The excluded external files are not all excluded because of conditional compilation: some also contain unsupported macro arguments, declaration modifiers, or vendored non-C++ token tricks. The conditional-placement gaps currently visible in excluded files are:

- Branch-local diagnostic macro runs used as portability scaffolding, for example RapidJSON's `#ifdef __clang__` branch in `rapidjson/pointer.h` that contains `RAPIDJSON_DIAG_PUSH` and `RAPIDJSON_DIAG_OFF(switch-enum)` before the next ordinary declaration. These marker-only branches are not part of the supported placement contract, even though the same configured macros may parse in ordinary statement or declaration positions.
- Ordinary selected common-body function starts are unsupported. One external example also mixes the start with branch-local sibling items: `googlemock/src/gmock_main.cc`, where the Windows branch supplies `#include <tchar.h>` and then `GTEST_API_ int _tmain(int argc, TCHAR** argv) {`, while the other branch supplies `GTEST_API_ int main(int argc, char** argv) {` and the shared function body starts after `#endif`.
Both shapes are outside the supported placement list in [preprocessor.md](preprocessor.md), and supporting either should be revisited only with a generic grammar shape.

Complete guarded GoogleTest-style macro function definitions, branch-selected complete statements, selected `TEST(...) {` common-body headers, and macro-interleaved string help fragments are not in this unsupported list: they parse with the GoogleTest style. The ignored `gmock-pp_test.cc` file passes a preprocessing-token generator into a template argument list, including `GMOCK_PP_FOR_EACH(..., ~, (int, float, double, char))`, so it is not evidence for conditional-placement support.

Other ignored GoogleTest files are also not conditional-placement evidence. Their remaining failures are macro-token-language cases such as preprocessor metaprogramming arguments, macro-generated declaration fragments, or matcher token sequences that are not normal C++ constructs at the use site. The exact generated fallback now covers the previously ignored semicolonless warning sentinels, local generator runs such as `GMOCK_INTERNAL_PARSE_FLAG(...)`, and stress-test macro bursts such as `THOUSAND_TESTS_(T)`.
